## App Concept
```
A note-taking "developer control center" app that lets users create, read, update, and delete
notes. Each note has a title and content body. Notes are displayed in reverse chronological
order. The app supports basic validation (title required), error handling (404 for missing
notes, flash messages for all operations), and persistent SQLite storage.

The same core feature set — full notes CRUD — is implemented across three distinct technology
stacks to compare developer experience, boilerplate overhead, and AI-assisted generation
across different ecosystems (Python/Django, Python/Flask, Node.js/React+Express).
```

===============

- CORS: frontend (port 3000) and backend (port 5000) are different origins — required explicit

- React state for optimistic UI: create prepends to local state before server confirms, with
  error rollback via setNotes(prevNotes) — needed careful handling to avoid stale state.
- sqlite3 in Node.js uses callback API, not Promise-based. Wrapped critical calls in explicit
  try/catch and relied on callbacks; a production app would use better-sqlite3 instead.
- Edit flow: initial generation had NoteList display-only with no way to pass selected note
  back to App for form pre-population — fixed with one follow-up prompt adding selectedNote
  state and onEdit callback.

b. Prompting (e.g. what required additional guidance; what worked poorly/well):
- server.js was generated cleanly: all 4 CRUD endpoints (GET/POST/PUT/DELETE), SQLite schema

  errors), CORS, body-parser.
- Component structure (App → NoteList + NoteForm + api.js service layer) was correct on
  first try — bolt.new conventions are well-represented in Claude's training data.
- Flash message auto-dismiss (setTimeout 3s) required explicit guidance.
- Two terminals required (backend + frontend) vs single process for Django/Flask — adds
  setup friction for development.

c. Approximate time-to-first-run and time-to-feature metrics:

  omitted the confirmation page. Fixed with a follow-up prompt.
